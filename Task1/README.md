# Реестр транзакций Saga

Основной процесс: создать платёж → списать средства → получить решение проверок → перевести деньги контрагенту или вернуть списание. Оркестратор управляет шагами Saga, а Payment Service хранит финансовые результаты.

| Транзакция | Описание | Тип | Компенсация |
| --- | --- | --- | --- |
| CREATE_PAYMENT | Зарегистрировать платёж, сумму, валюту и участников. Сохранить идентификатор процесса | компенсируемая | CANCEL_PAYMENT |
| CANCEL_PAYMENT | Зафиксировать отказ или отмену зарегистрированного платежа. Историю не удалять; при наличии списания завершать отмену только после возврата | повторяемая | — |
| DEBIT_FUNDS | Списать сумму со счёта клиента и подтвердить результат | компенсируемая | REFUND_FUNDS |
| CHECK_FRAUD | Запросить антифрод-проверку. Получить ALLOW, DENY либо MANUAL; отсутствие ответа приводит к ожиданию | повторяемая | — |
| CHECK_COMPLIANCE | Получить решение внешних compliance-проверок; детализация и реализация вне проекта | повторяемая | — |
| CHECK_LIMITS | Получить результат проверки ограничений без изменения лимита; реализация вне проекта | повторяемая | — |
| RECORD_DECISION | Сохранить окончательное решение, источник и время; при DENY заблокировать перевод. Источник: FraudCheck, оператор либо cut-off | повторяемая | — |
| TRANSFER_FUNDS | Подтверждённо перевести средства контрагенту. Успешное завершение — pivot исходной Saga | необратимая | — |
| REFUND_FUNDS | Вернуть подтверждённое списание клиенту до успешного перевода контрагенту | повторяемая | — |
| FINISH_REFUND | Зафиксировать завершённый возврат после подтверждения REFUND_FUNDS | повторяемая | — |
| NOTIFY_CUSTOMER | Сообщить клиенту о проведении или возврате платежа | повторяемая | — |
| NOTIFY_SECURITY | Передать сведения о подозрительной операции службе безопасности | повторяемая | — |
| CREATE_REFUND | Зарегистрировать отдельный возврат после завершения исходного платежа: по запросу клиента или fraud-постфактум | повторяемая | — |
| REFUND_SETTLED_PAYMENT | Исполнить возврат по завершённому платежу в отдельном процессе; сохранить связь с исходным переводом | необратимая | — |

## Граница компенсации

До pivot отказ проверки блокирует перевод и запускает REFUND_FUNDS. Уведомление безопасности идёт параллельно. Подтверждённый отказ перевода также приводит к возврату.

После pivot отмена клиентом или позднее обнаружение мошенничества запускают отдельный возврат через CREATE_REFUND и REFUND_SETTLED_PAYMENT. Его источник финансирования и взаимодействие с контрагентом требуют отдельного договора с платёжным провайдером; В прототипе этот процесс не реализован.

Ошибка уведомления после перевода вызывает повтор уведомления без денежных операций.

## Правила повторов и ожиданий

В целевой системе каждый денежный обработчик принимает ключ операции и при повторе возвращает прежний результат. Повтор REFUND_FUNDS не должен повторно зачислять деньги.

После тайм-аута денежного запроса результат сверяют по ключу операции. Cut-off относится только к проверкам.

Ручное рассмотрение и таймер не выделены как финансовые транзакции. У оператора есть 20 минут на ALLOW или DENY; затем решение по cut-off фиксируется с источником `cutoff`.

При компенсации нескольких шагов сначала возвращается подтверждённое списание через REFUND_FUNDS, затем закрывается платёж через CANCEL_PAYMENT. Компенсация регистрации не удаляет запись и не должна скрывать незавершённый возврат.
